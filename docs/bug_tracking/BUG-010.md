# BUG-010 — A panic in reservation create permanently leaks the global write mutex

**Status:** fixed in `05e94ed` · **Component:** core · **Severity:** high
**Found:** 2026-07-30 · **Version:** v2.3.2

Index: [bug_tracker.md](bug_tracker.md)

---

## Location

`internal/app/igor-server/reservation_handlers.go:27-55`, `handleCreateReservations`:

```go
func handleCreateReservations(w http.ResponseWriter, r *http.Request) {

	dbAccess.Lock()
	createParams := getBodyFromContext(r)
	clog := hlog.FromRequest(r)
	actionPrefix := "create reservation"
	clog.Debug().Msgf("handling %s request", actionPrefix)
	rb := common.NewResponseBody()

	res, resIsNow, status, err := doCreateReservation(createParams, r)
	dbAccess.Unlock()
	...
```

## Cause

The unlock is a bare statement, not a `defer`. If `doCreateReservation` panics, the panic
unwinds past line 37 and `dbAccess` is never released.

The panic does not crash the process, because `httprouter` recovers it — `PanicHandler` is
registered at `routes.go:26` and invoked from the router's deferred `recv`
(`httprouter/router.go:309-313`). The server therefore keeps running, keeps serving reads,
and keeps accepting connections, while its global write mutex is held by a goroutine that
no longer exists.

`handleCreateReservations` is the **only** write handler that unlocks without `defer`.
Every other one — `handleUpdateReservation` (`reservation_handlers.go:105-106`),
`handleDeleteReservations` (`:129-130`), the host, group, user, distro, profile, cluster
and kickstart handlers — uses `defer dbAccess.Unlock()`, which releases the mutex during
panic unwinding. The exposure is specific to reservation create.

Three other non-deferred unlocks exist (`server.go:252-256`, `server.go:382-390`,
`distro_initrd_info.go:149-157`) but none is in an HTTP handler. Those run on goroutines
with no `recover()` anywhere in the package, so a panic there terminates the process
instead of leaking the lock — a loud failure rather than a silent one.

## Reproduction

Requires a panic inside `doCreateReservation`. [BUG-011](BUG-011.md) is a demonstrated,
reachable one: `findBestSolution` indexes a zero-length slice and is called from
`scheduleHostsByAvailability` (`scheduling.go:115`), which `doCreateReservation` invokes at
`reservation_create.go:334`.

The leak itself follows from Go's defer semantics and needs no separate demonstration: a
`sync.Mutex` locked without a deferred unlock, whose holder panics past the unlock
statement, stays locked. `sync.Mutex` has no owner tracking and no reentrancy, so nothing
detects or recovers it.

**Not reproduced end to end against a running server.** The mechanism is established from
the source and from the panic in BUG-011; the composite has not been exercised on a live
instance.

## Impact

Permanent, silent, server-wide write outage from a single malformed or unlucky
`igor res create`:

- Every subsequent write — create, delete, update, extend, host, group, user — blocks
  forever on `dbAccess.Lock()`.
- Reads keep working, because read handlers take no lock, so the server looks healthy.
- `closeoutReservations` blocks on the same mutex (`scheduling.go:283`), so expired
  reservations are never cleaned up and never release their nodes.
- The process cannot be shut down gracefully — see [BUG-013](BUG-013.md) — so recovery
  requires SIGKILL.

The client that triggered it does not even get an error page, because
[BUG-014](BUG-014.md) causes `panicHandler` to re-panic before it writes the 500 response.

Unlike an ordinary panic, nothing in `igor.log` reports a *write outage*: the handler's
Info line is emitted only after `doCreateReservation` returns
(`reservation_handlers.go:51`), which never happens. A `PANIC` level line **is** written
by `panicHandler` (`handler_util.go:80`) before it re-panics, so grepping the log for
`PANIC` is the fastest way to confirm or rule out this bug after an incident.

## Resolution

Fixed in `05e94ed` by adding `lockedDbWrite` to `database.go`, which runs a function while
holding `dbAccess` and defers the release, then using it in `handleCreateReservations`.

The locked region has to end before `manageReservations` further down the handler, which
takes `dbAccess` itself, so the helper exists to give the region a scope of its own. The
comments at both sites state that a plain `defer dbAccess.Unlock()` at the top of the
handler is **not** a valid substitute — it self-deadlocks on every immediate-start
reservation — because that is the obvious-looking wrong fix.

The three other non-deferred unlocks were converted at the same time:
`fillKernelInfoBacklog` and `ldapSyncManager` in `server.go`, and `processInitrdJob` in
`distro_initrd_info.go`. Those run on goroutines with no `recover()`, so a panic there
terminates the process rather than leaking the mutex; the change is for consistency and
against a future `recover()` being added, not for an observed leak. No bare
`dbAccess.Unlock()` now remains outside test code.

Covered by three tests in `internal/app/igor-server/database_test.go`:
`TestLockedDbWriteReleasesOnNormalReturn`, `TestLockedDbWriteReleasesOnPanic`, and
`TestLockedDbWriteUsableAfterPanic`. All three were confirmed to fail against the previous
pattern by temporarily reverting the helper to a bare unlock — the panic case reports the
leak, and the follow-up writer hangs until the test timeout, which is the production
symptom in miniature.

Note this removes the *consequence* of a panic in the create path, not any panic source.
[BUG-011](BUG-011.md) remains open and can still fail a reservation create request; it can
no longer take the server's writes down with it.

### Original suggested resolution

Change the unlock to a `defer` immediately after the `Lock()`:

```go
dbAccess.Lock()
defer dbAccess.Unlock()
```

This requires care rather than a blind edit. The current code deliberately unlocks
*before* calling `manageReservations(&now, installReservations)` at
`reservation_handlers.go:41`, because `installReservations` takes `dbAccess` itself
(`scheduling.go:505`) and `sync.Mutex` is not reentrant. Deferring the unlock to the end
of the function would self-deadlock on every immediate-start reservation.

The correct shape extracts the locked region into its own function so the `defer` scope
ends before `manageReservations` is called:

```go
res, resIsNow, status, err := func() (*Reservation, bool, int, error) {
    dbAccess.Lock()
    defer dbAccess.Unlock()
    return doCreateReservation(createParams, r)
}()
```

Auditing the other three non-deferred unlocks for the same treatment is worthwhile even
though they fail loudly rather than silently.
