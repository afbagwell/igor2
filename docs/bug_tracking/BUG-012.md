# BUG-012 — Host delete/update blocks all writes on an unbuffered channel send

**Status:** open · **Component:** core · **Severity:** medium
**Found:** 2026-07-30 · **Version:** v2.3.2

Index: [bug_tracker.md](bug_tracker.md)

---

## Location

`internal/app/igor-server/server.go:32`:

```go
clusterUpdateChan = make(chan struct{})     // unbuffered
```

Senders, both reached while `dbAccess` is held:

```go
clusterUpdateChan <- struct{}{}             // host_delete.go:78,  in doDeleteHost
clusterUpdateChan <- struct{}{}             // host_update.go:69,  in doUpdateHost
clusterUpdateChan <- struct{}{}             // cluster_create.go:243
```

Sole receiver: `hostProbeManager` (`probe_manager.go:59`).

## Cause

The channel is unbuffered, so the send blocks until the probe manager reaches its `select`.
`handleDeleteHosts` (`host_handlers.go:383-384`) and the host update handler
(`host_handlers.go:101-102`) both hold `dbAccess` for the whole operation, so the sending
goroutine blocks while holding the global write mutex.

`hostProbeManager` leaves its `select` for the entire duration of a probe sweep
(`probe_manager.go:80-115`), which runs three probes in sequence:

```go
igor.PowerProbe.probeHosts(hostList)                  // ipmitool, one process per host
igor.PortProbe.probeHosts(getPoweredHosts(hostList))
igor.PingProbe.probeHosts(getPoweredHosts(hostList))
```

`PowerProbe` goes through `runAllCapture` → `DefaultRunner` (`probe_power.go:28`), so its
duration is governed by `externalCmds.concurrencyLimit`, `externalCmds.commandRetries` and
the 2s per-command timeout. On a 275-node cluster with `concurrencyLimit: 3` and
`commandRetries: 1` (attempts = 2):

| Case | Sweep duration |
|---|---|
| Healthy, ~0.4s per call | 275 × 0.4 / 3 ≈ **37s** |
| Every host timing out | 275 × (2 + 1 + 2) / 3 ≈ **7.6 minutes** |

So a host delete can block every write on the server for up to several minutes, and the
worst case coincides exactly with the situation in which an administrator is most likely to
be deleting hosts — a cluster containing dead nodes that time out in every sweep.

A second, more severe variant: `hostProbeManager` is started only when the database has
hosts at boot (`exec.go:56-59`):

```go
if len(hostList) > 0 {
    wg.Add(1)
    go hostProbeManager(hostList)
}
```

On an instance started with no hosts registered, there is no receiver at all and the send
blocks **forever**, permanently wedging the mutex on the first host or cluster operation.

## Reproduction

`igor host delete <name>` or `igor host edit <name> ...` on a cluster large enough for the
probe sweep to be non-trivial. The delay is observable as the command taking far longer
than the database work warrants, with every other write command queued behind it.

The unbuffered-send-blocks-without-a-receiver property is a language guarantee and needs no
demonstration. What is established from the source is that the send is made under
`dbAccess` and that the only receiver is unavailable for the length of a probe sweep.

**Not reproduced against a running server.** Sweep durations above are computed from the
configured knobs rather than measured.

## Impact

Every write operation server-wide stalls for the duration of one probe sweep — seconds to
minutes depending on cluster size and BMC health — whenever a host is added, edited or
deleted, or a cluster is created. Reads are unaffected.

Automatic reservation cleanup is stalled for the same window, since `closeoutReservations`
waits on the same mutex.

In the no-hosts-at-boot case the stall is permanent and requires killing the process.

This is a *bounded* stall in the normal case, which distinguishes it from
[BUG-008](BUG-008.md): a write outage that never clears without a restart is not explained
by this bug unless the probe manager was never started.

## Suggested resolution

1. Give the channel a small buffer and make the send non-blocking, so a busy or absent
   probe manager cannot stall a database operation:

   ```go
   clusterUpdateChan = make(chan struct{}, 1)
   ...
   select {
   case clusterUpdateChan <- struct{}{}:
   default:   // a refresh is already pending; coalescing is correct here
   }
   ```

   Coalescing is safe because the receiver re-reads the full host list from the database
   (`probe_manager.go:60`) rather than acting on the message contents.

2. Move the send outside the `dbAccess` critical section regardless.

3. Start `hostProbeManager` unconditionally, or make the send safe when it is absent. The
   `len(hostList) > 0` guard creates a state in which a normal administrative action
   deadlocks the server.
