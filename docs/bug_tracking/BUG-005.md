# BUG-005 — `helpLink` is used as an email recipient, so the account-removal alert is never delivered

**Status:** fixed in `f5aa095` · **Component:** core · **Severity:** medium
**Found:** 2026-07-30 · **Version:** v2.3.2

Index: [bug_tracker.md](bug_tracker.md)

---

## Location

`internal/app/igor-server/notify.go:353-361`, the `EmailAcctRemovedIssue` case of
`processAcctNotifyEvent`:

```go
case EmailAcctRemovedIssue:
    subj = "auto-removal of igor account needs review"
    admin, _, _ := getIgorAdminTx()
    if len(admin.Email) != 0 {
        addEmailToList(&toList, admin.Email)
    } else {
        addEmailToList(&toList, igor.Email.HelpLink)
    }
```

## Cause

`igor.Email.HelpLink` is a **web address**, not an email address.
`conf/igor-server.yaml:390` documents it as "An optional link that points to a cluster
admin team's FAQ/support page or other help resource", and every template consumes it as
one — `<a href="{{.HelpLink}}">{{.HelpLink}}</a>` in `SenderInfoTemplate`. Using it as a
recipient hands gomail something like `https://wiki.example.com/igor` where it expects an
RFC 5322 address.

Unlike the empty-recipient case in [BUG-004](BUG-004.md), gomail does *not* fail silently
here: `getRecipients` calls `parseAddress`, which wraps `net/mail.ParseAddress`. That
rejects a URL — `mail.ParseAddress("https://wiki.example.com/igor")` returns
`mail: missing '@' or angle-addr` — so the send aborts with `gomail: invalid address`.

Note the ordering: `DialAndSend` (`smtp.go:203-211`) calls `Dial` **first** and only then
`Send`, which is where recipients are parsed. So the connection to the SMTP server is
opened and torn down on every attempt before the address is ever rejected.

## Reproduction

The fallback branch is the **default** path, not an edge case: `igor-admin` is seeded
with `Email: ""` at `database.go:136-140` and nothing sets it during normal setup. So on
any deployment where the admin has not manually given `igor-admin` an address and
`helpLink` is configured, the branch is taken with a URL.

Trigger the alert by letting LDAP sync auto-remove a user who owns a reservation or
distro (`ldap.go:563-568`).

`TestAcctRemovedIssueWarnsInsteadOfEmailingHelpLink` in `notify_test.go` reproduces it
against an in-memory database seeded with `igor-admin` exactly as `database.go` creates
it. Against the unfixed code the call returns an error rather than logging the alert:

```
Error:    Received unexpected error:
          dial tcp 127.0.0.1:1: connect: connection refused
Error:    "" does not contain "no email address configured"
```

The dial error is the test harness pointing at a dead port — the significant part is
that the unfixed code *attempted a send at all*, and that nothing was logged. Against a
reachable SMTP server that same attempt returns `gomail: invalid address`.

Not reproduced against a live SMTP server; the `invalid address` outcome rests on the
gomail source plus a direct check that `net/mail.ParseAddress` rejects a URL.

## Impact

The one alert that tells administrators "resources were just re-assigned to igor-admin
and need review" is the alert that fails to send. The re-assignment still happens, so
groups, reservations and distros silently accumulate under `igor-admin` ownership with
nobody notified. Logged as an error, but the operational signal is lost.

Note that when `helpLink` is *also* unset, `toList` ends up empty and the send fails with
a clear `NoEmailRecipientError` instead — so the failure mode differs by configuration,
which is part of why this went unnoticed.

## Resolution

The `helpLink` fallback is removed outright. There is no configured alternative recipient
to put in its place, so when `igor-admin` has no address the alert is written to the log
as a warning instead, naming the removed account and stating why no email went out:

```
account 'departed' was auto-removed and one or more of its groups, reservations and/or
distros were re-assigned to igor-admin, but no alert could be sent because igor-admin has
no email address configured - review the re-assigned resources manually
```

`processAcctNotifyEvent` then returns `nil` — no send is attempted, so nothing dials and
the notification manager does not log a second, redundant error line.

Two further corrections in the same block:

- `getIgorAdminTx`'s error was discarded (`admin, _, _ :=`), and `admin` is nil on the
  error path, so `len(admin.Email)` would have panicked on any database failure. The
  error is now returned.
- The check is `admin.Email == ""` rather than `len(admin.Email) != 0` with an inverted
  body, which reads straightforwardly now that the fallback branch is gone.

Covered by `TestAcctRemovedIssueWarnsInsteadOfEmailingHelpLink` and
`TestAcctRemovedIssueEmailsAdminWhenAddressIsSet` in
`internal/app/igor-server/notify_test.go`; the first was confirmed to fail against the
original code. The pair runs against an in-memory SQLite database wired in through the
`IGormDb` interface, which is the first database-backed test in this package.

## Relationships

| Relationship | Bug | Note |
|---|---|---|
| related to | [BUG-004](BUG-004.md) | Shares the precondition that `igor-admin` is seeded with no email. Isolated — either can be fixed first. |

Both bugs are downstream of the same fact: `igor-admin` has `Email: ""` by default, and
both notification paths cope with that badly. They are nevertheless **isolated**.
BUG-004's failure is an empty recipient list that gomail accepts, so the SMTP conversation
itself fails at `DATA`; this one's is a syntactically invalid address that gomail rejects
after connecting but before any SMTP command is issued. The BUG-004 fix does not touch
this branch, and fixing this one would not have prevented the 503. Neither blocks the
other.

Giving `igor-admin` a real address at setup would defuse both, but that is a
configuration and migration question rather than a code fix, and is deliberately out of
scope here — this fix makes the code correct when no address exists, which it must be
either way.
