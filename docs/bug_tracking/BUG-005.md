# BUG-005 — `helpLink` is used as an email recipient, so the account-removal alert is never delivered

**Status:** open · **Component:** core · **Severity:** medium
**Found:** 2026-07-30 · **Version:** v2.3.2

Index: [bug_tracker.md](bug_tracker.md)

---

## Location

`internal/app/igor-server/notify.go:353-361`, the `EmailAcctRemovedIssue` case of
`processAcctNotifyEvent`:

```go
case EmailAcctRemovedIssue:
    subj = "auto-removal of igor account needs review"
    admin, _, _ := getIgorAdminTx()
    if len(admin.Email) != 0 {
        addEmailToList(&toList, admin.Email)
    } else {
        addEmailToList(&toList, igor.Email.HelpLink)
    }
```

## Cause

`igor.Email.HelpLink` is a **web address**, not an email address.
`conf/igor-server.yaml:390` documents it as "An optional link that points to a cluster
admin team's FAQ/support page or other help resource", and every template consumes it as
one — `<a href="{{.HelpLink}}">{{.HelpLink}}</a>` in `SenderInfoTemplate`. Using it as a
recipient hands gomail something like `https://wiki.example.com/igor` where it expects an
RFC 5322 address.

Unlike the empty-recipient case in [BUG-004](BUG-004.md), gomail does *not* fail silently
here: `getRecipients` calls `parseAddress`, which returns an error for an unparseable
value, so the send aborts with `gomail: invalid address`. The email is simply never sent.

## Reproduction

The fallback branch is the **default** path, not an edge case: `igor-admin` is seeded
with `Email: ""` at `database.go:136-140` and nothing sets it during normal setup. So on
any deployment where the admin has not manually given `igor-admin` an address and
`helpLink` is configured, the branch is taken with a URL.

Trigger the alert by letting LDAP sync auto-remove a user who owns a reservation or
distro (`ldap.go:563-568`).

Not yet reproduced against a running instance — this is read from the source and the
gomail contract, and should be confirmed on a DEVMODE server before the fix is designed.

## Impact

The one alert that tells administrators "resources were just re-assigned to igor-admin
and need review" is the alert that fails to send. The re-assignment still happens, so
groups, reservations and distros silently accumulate under `igor-admin` ownership with
nobody notified. Logged as an error, but the operational signal is lost.

Note that when `helpLink` is *also* unset, `toList` ends up empty and the send fails with
a clear `NoEmailRecipientError` instead — so the failure mode differs by configuration,
which is part of why this went unnoticed.

## Relationships

| Relationship | Bug | Note |
|---|---|---|
| related to | [BUG-004](BUG-004.md) | Shares the precondition that `igor-admin` is seeded with no email. Isolated — either can be fixed first. |

Both bugs are downstream of the same fact: `igor-admin` has `Email: ""` by default, and
both notification paths cope with that badly. They are nevertheless **isolated**.
BUG-004's failure is an empty recipient list reaching the SMTP conversation; this one's
is a syntactically invalid address, caught by gomail before any connection is made. The
BUG-004 fix does not touch this branch, and fixing this one would not have prevented the
503. Neither blocks the other.

A durable fix for both would likely give `igor-admin` a real address at setup, which is a
configuration and migration question rather than a code fix, and is why this is filed
`open` rather than folded into the BUG-004 commit.
