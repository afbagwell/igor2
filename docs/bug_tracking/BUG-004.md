# BUG-004 — Reservation owned by a user with no email retries a warning every minute forever

**Status:** fixed in `267035c` · **Component:** core · **Severity:** medium
**Found:** 2026-07-30 · **Version:** v2.3.2

Index: [bug_tracker.md](bug_tracker.md)

---

## Symptom

A production deployment logs this at the top of every wall-clock minute, twice each time:

```
gomail: could not send email 1: 503 5.5.2 Need rcpt command
```

## Location

Three cooperating sites in `internal/app/igor-server/notify.go`.

**1. The address that bypasses the filter** — `processResNotifyEvent`, line 578:

```go
if strings.HasPrefix(msg.Res.Group.Name, GroupUserPrefix) {
    toList = append(toList, msg.Res.Owner.Email)
```

Every other recipient in the file is added through `addEmailToList`, which drops the
empty string. This one call appends `Owner.Email` unconditionally, so an owner with no
email on file contributes `""` to the list.

**2. The guard that counts the wrong list** — `sendEmail`, lines 636-638 and 654-665:

```go
if len(toList) == 0 && len(ccList) == 0 && len(bccList) == 0 {
    return fmt.Errorf("no recipient address for outbound email, subject: %v", subject)
}
...
m.SetHeader("To", dedupeEmailList(toList)...)
```

The guard counts the **raw** list, but the header is set from the **deduped** list.
`dedupeEmailList` runs the addresses through `common.Set`, which by documented design
silently discards empty and whitespace-only keys (`internal/pkg/common/set.go:30-37`).
So `toList = [""]` has length 1, passes the guard, and then becomes a zero-length
variadic call — `m.SetHeader("To")`.

**3. The state update that never runs** — `processResNotifyEvent`, lines 599-623. The
`NextNotify` write for `EmailResWarn` / `EmailResFinalWarn` sits *after* the
`sendEmail` error return, so a failed send leaves `NextNotify` untouched.

## Cause

`gomail.Message.SetHeader` with no values stores an **empty but present** header:

```go
func (m *Message) SetHeader(field string, value ...string) {
    m.encodeHeader(value)
    m.header[field] = value
}
```

`getRecipients` (`gopkg.in/mail.v2@v2.3.1/send.go:76-98`) then finds the key present,
iterates zero addresses, and returns an **empty slice and a nil error**. It does not
treat "no recipients" as a failure. gomail proceeds to `MAIL FROM`, issues no `RCPT TO`,
and sends `DATA` — which is a bad command sequence, so the server answers `503 5.5.2`.

The every-minute repetition is site 3. `manageReservations(&checkTime, sendExpirationWarnings)`
runs at the top of every minute (`server.go:292`), and `sendExpirationWarnings` re-queues
the warning whenever `r.NextNotify >= ResNotifyTimes[i]` (`scheduling.go:626-629`).
Because the failed send skipped the `NextNotify` write, that condition stays true, and
the same undeliverable warning is regenerated every minute until the reservation ends.

The doubling is **not** two send attempts — `d.RetryFailure` is explicitly `false`. It is
double logging: `sendEmail` logged the error at line 682 *and* returned it to
`notificationManager`, which logged it again at `server.go:326`.

## Reproduction

The owner reaches the empty-email state through a supported path, not an exotic one.
`igor-admin` is seeded with `Email: ""` at `database.go:136-140`:

```go
igorAdmin := &User{
    Name:     IgorAdmin,
    Email:    "",
    PassHash: passHash,
}
```

When LDAP sync auto-removes a user, every reservation they own is re-assigned to
`igor-admin` (`ldap.go:524-541`). That re-assignment also moves the reservation into the
new owner's pug (`reservation_update.go:675-678`, `changes["GroupID"] = newPugID`), so
`msg.Res.Group.Name` carries `GroupUserPrefix` and `processResNotifyEvent` takes the
line-578 branch. As the inherited reservation approaches expiry, the warning fires and
fails, every minute, until it ends.

`TestSendEmailRejectsUnusableRecipients` in `notify_test.go` reproduces the send half
directly. Against the unfixed code it fails as follows — note that the first three cases
reached the dialer, which is the code path that draws the 503 from a real SMTP server:

```
empty owner address: expected NoEmailRecipientError, got dial tcp 127.0.0.1:1: connect: connection refused
whitespace owner address: expected NoEmailRecipientError, got dial tcp 127.0.0.1:1: connect: connection refused
unusable across all three headers: expected NoEmailRecipientError, got dial tcp 127.0.0.1:1: connect: connection refused
```

The fourth case (`nil` lists) already returned the old error, confirming the existing
guard works — it is only blind to a list whose contents are dropped downstream.

## Impact

Log noise at one entry per minute per affected reservation, doubled, indefinitely.
No data loss and no effect on reservation scheduling, but it buries real errors in the
server log and opens a needless TCP connection to the SMTP server every minute. The
notification itself is undeliverable either way — nobody attached to the reservation has
an address — so no user misses an email that could otherwise have been sent.

## Resolution

- `sendEmail` now normalizes `toList` / `ccList` / `bccList` **before** the emptiness
  check and sets the headers from those same normalized slices, so the value counted and
  the value sent can no longer disagree.
- The guard returns a typed `NoEmailRecipientError` (`error.go`) rather than a bare
  `fmt.Errorf`, per CLAUDE.md §7.
- `processResNotifyEvent` treats `NoEmailRecipientError` as permanent: it logs a warning
  and falls through to the `NextNotify` write, so a warning threshold is recorded as
  handled instead of being retried forever. Any other send error still returns early and
  will be retried, which is the right behavior for a transient SMTP outage.
- The line-578 `append` now uses `addEmailToList`, matching every other recipient site.
- `sendEmail` no longer logs the error it returns, removing the duplicate log line.

Covered by `TestSendEmailRejectsUnusableRecipients`, `TestSendEmailAcceptsUsableRecipient`
and `TestDedupeEmailListDropsUnusableAddresses` in
`internal/app/igor-server/notify_test.go`. The first was confirmed to fail against the
original code.

Not verified against a live SMTP server; the reproduction rests on the gomail source and
the unit test above rather than on an observed 503 in DEVMODE.
