# BUG-018 — Every multipart upload strands its spooled file until /tmp fills

**Status:** fixed (`16a4a0b`) · **Component:** core · **Severity:** high
**Found:** 2026-08-12 · **Fixed:** 2026-08-12 · **Version:** v2.3.2

Reported from operations, not from code analysis.

Index: [bug_tracker.md](bug_tracker.md)

---

## Location

`ParseMultipartForm` spools any part larger than `MaxMemory` to disk. `MaxMemory` is 32MB
(`distro.go:30-31`), and a kernel/initrd pair always exceeds it, so every upload writes a
`multipart-*` file into `os.TempDir()` — `/tmp` unless `TMPDIR` says otherwise.

Five call sites, in three validators:

```go
r.ParseMultipartForm(MaxMemory)   // distro_handlers.go:133, :281   (validateDistroParams)
                                  // kickstart_handler.go:118, :143 (validateKSParams)
                                  // distro_image_handler.go:93     (validateDistroImageParams)
```

## Cause

**Corrected 2026-08-12.** This section first attributed the leak to panics escaping
`ServeHTTP` (BUG-014) and stated that ordinary uploads did not leak. Both were wrong, and the
severity was raised from medium to high as a result. The measurement behind the original
reading mounted the handler directly on the router, which shares the request object with
`net/http` and lets the stdlib cleanup work — a shape igor never uses. The report of 30 files
accumulated from ordinary uploads is what exposed the error. The real cause follows.

`net/http` does clean these up, but only for the request object it holds itself
(`net/http/server.go:1700-1720`):

```go
func (w *response) finishRequest() {
    ...
    if w.req.MultipartForm != nil {
        w.req.MultipartForm.RemoveAll()
    }
}
```

igor never parses that request. `hlog.NewHandler` is the first entry in `hcDefaultChain`
(`routes.go`) and does `r = r.WithContext(...)`, which **shallow-copies** the `http.Request`.
`paramsHandler` (`middleware.go:45-49`) and `authnHandler` (`authn.go:89`) copy it again. By
the time a validator calls `ParseMultipartForm`, it is writing `MultipartForm` onto a copy
several removes from `w.req`.

`w.req.MultipartForm` therefore stays `nil` for the whole request, `finishRequest` skips the
cleanup, and the spooled file survives — **on every upload, whether or not anything goes
wrong**. Nothing else ever removed it.

A second, independent path leaks the same file even when the stdlib cleanup would have
applied: `finishRequest` is called as a plain statement, not deferred
(`net/http/server.go:2116`), so a panic escaping `ServeHTTP` unwinds past it. igor makes that
certain, because `panicHandler` logs through `logger.Panic()`, which panics again — that is
[BUG-014](BUG-014.md). This path is real but secondary; it was not needed to produce the
reported outage.

### The reported symptom, and why it is a second defect

Once `/tmp` is full the operator does not see a disk error. They see:

```
igor: Post https://igor-ip:8443/igor/distros: write tcp src->dst: use of closed network connection
```

That comes from a separate defect in the same code. Three of the five parse sites called the
next handler *after* writing the validation error:

```go
if validateErr = r.ParseMultipartForm(MaxMemory); validateErr != nil {
    clog.Warn().Msgf("validateDistroParams - %v", validateErr)
    createValidationErrMessage(validateErr, w)
    handler.ServeHTTP(w, r)      // <-- runs the real handler anyway
    return
}
```

`ParseMultipartForm` leaves `r.MultipartForm` nil when it fails, and `doCreateDistro`
dereferences that field (`distro_create.go:91`, `len(r.MultipartForm.File)`). So a full
`/tmp` produced: 400 written → handler runs regardless → nil pointer dereference → panic →
`panicHandler` re-panics → connection dropped without a readable response. The client's
write fails and reports a closed connection.

The other two sites already returned, and so does the same function's own terminal error
branch (`distro_handlers.go`, `if validateErr != nil { ...; return }`), so this was
inconsistent with the surrounding code rather than deliberate.

### Third defect: every parse failure was a client error

`createValidationErrMessage` (`handler_util.go:106-110`) always answers `400 Bad Request`
with `validateErr.Error()` verbatim. A temp directory that is full, read-only or missing is
not a malformed request. Reporting 400 tells an administrator to go and look at the command
they typed, and the raw text hands the client server-side paths, contrary to §4.

## Reproduction

Observed first in production: 30 `multipart-*` files in `/tmp`, filling 99% of a 32GB
filesystem, after which `igor distro create` failed for everyone. Deleting them by hand
restored service immediately. Thirty files is thirty ordinary uploads — not thirty crashes.

Measured against a real `httptest` server with `TMPDIR` redirected and a file part above
`maxMemory`. The mount shape is the whole story:

| Handler mount | Files left after a **successful** upload |
|---|---|
| Mounted directly on the router | 0 |
| Behind `hlog.NewHandler` — **igor's actual chain** | **1** |
| Behind the full copy stack (hlog + user context) | **1** |

The first row is why this went unnoticed: a handler wired straight to the router shares the
request object with `net/http`, so the stdlib cleanup works and nothing leaks. Igor never
wires one that way.

Panic behaviour, measured separately, is the secondary path:

| Scenario (direct mount, so the stdlib cleanup applies) | Files left |
|---|---|
| Handler parses, returns normally | 0 |
| Handler parses, then panics — igor's real `panicHandler` | **1**, client got `EOF` |
| Handler parses, then panics — `PanicHandler` that does not re-panic | 0 |

And the shape of the fix, measured on the panic path:

| Cleanup strategy | Files left after a panic |
|---|---|
| None | 1 |
| **`defer` `RemoveAll` in the parsing frame** | **0** |
| `RemoveAll` called after the handler returns, not deferred | 1 |

## Impact

`/tmp` gains one kernel-plus-initrd spool file per upload, permanently. Nothing in igor or in
`net/http` ever removes it. A site that registers images regularly fills its temp filesystem
as a matter of course, and from that point no distro or image can be created by anyone.

Recovery requires shell access to the server to delete the files. Nothing in igor reports the
cause, and the client is told only that the connection closed.

Severity is high: it needs no unusual trigger, no error and no panic — ordinary successful
use is sufficient, so it is a matter of when rather than whether. It takes out distro and
image creation completely and cannot be cleared from the CLI. It is not `high` in the sense
BUG-008 or BUG-017 are, since it does not wedge the whole server; reservations and everything
else keep working throughout.

## Resolution

Fixed in `16a4a0b`, in three parts.

**1. `removeUploadTempFiles` (`handler_util.go`), deferred in each of the three validators.**
Both properties are load-bearing, for different reasons:

- *In the frame that parses* — this is what fixes the reported outage. Only that frame holds
  the request copy `MultipartForm` was written onto. A wrapper mounted anywhere above `hlog`
  holds an earlier copy whose field is `nil`, which is precisely the mistake `net/http` is
  already making on igor's behalf; repeating it in igor's own middleware would have looked
  like a fix and changed nothing.
- *Deferred* — this covers the panic path, where no cleanup placed after the work runs at
  all. Measured: the non-deferred variant still leaves the file behind.

`RemoveAll` ignores files that are already gone, so it is safe whether or not `net/http`
also gets there.

**2. The three validators no longer call the next handler after a validation failure.** This
removes the nil-dereference panic, and with it the dropped connection.

**3. `respondUploadParseErr` (`handler_util.go`) classifies the failure.** An error carrying
an `fs.PathError` means the server could not write the spool file: `503 Service Unavailable`
with a message naming what an administrator should check. Anything else stays `400`. The
underlying error goes to the log only, since it names server paths.

The discriminator is `errors.As(err, *fs.PathError)` rather than a list of errno values:
everything `mime/multipart` does against the filesystem produces one, and its parse errors
do not, so it does not need extending for the next filesystem failure mode.

### Covering tests

In `internal/app/igor-server/upload_cleanup_test.go`:

| Test | What it pins |
|---|---|
| `TestUploadTempFilesRemovedWhenHandlerPanics` | The bug itself: a real server, igor's real `panicHandler`, a panic after a successful upload, and nothing left in TMPDIR. |
| `TestUploadTempFilesRemovedOnNormalReturn` | The paths that already worked still work, and the double `RemoveAll` is harmless. |
| `TestRemoveUploadTempFilesHandlesUnparsedRequest` | Safe on a request that never parsed a form — every validator defers it before knowing the body is multipart. |
| `TestUploadParseErrorOnUnwritableTempDirIsNotClientError` | A read-only temp directory yields 503, an actionable message, and no server path in the body. |
| `TestUploadParseErrorOnMalformedBodyStaysClientError` | A malformed body is still 400. |
| `TestEveryMultipartParserDefersCleanup` | Every frame calling `ParseMultipartForm` also defers the cleanup. Confirmed to fail when the defer is removed from `validateDistroParams`. |

The last one is the durable protection. A new upload route that forgets the defer
reintroduces this silently, and the consequence only appears as a full disk weeks later.

### What was not done

[BUG-014](BUG-014.md) was *not* the cause of this bug — that was the initial reading, and it
was wrong (see the correction note under Cause). Fixing it would not have stopped the leak,
because `finishRequest` would still have found `nil` on the request it holds. It has since
been fixed in `88a9471` on its own account: it governs every panic in the server, and it is
why an operator saw a closed connection here instead of a 500.

Staged image files under `imageStagePath` are a separate concern and are untouched here. That
path is `$IGOR_HOME/igor_staged_images` by default (`config.go:461`), not `/tmp`, so it is not
what the report describes — but `stageUploadedFiles` does orphan an already-staged kernel when
the initrd upload fails, and `registerImage` discards the `tempFiles` it returns on that path.
Not filed yet; noted here so it is not lost.
