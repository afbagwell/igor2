# BUG-009 — Power commands run with no timeout while holding the global write mutex

**Status:** open · **Component:** core · **Severity:** high
**Found:** 2026-07-30 · **Version:** v2.3.2

Index: [bug_tracker.md](bug_tracker.md)

---

## Location

`internal/app/igor-server/host_power.go`, all four `runAll` call sites in `doPowerHosts`:

```go
runAll(igor.ExternalCmds.PowerOff, hostList, 0)              // :109
runAll(igor.ExternalCmds.PowerCycle+oioFlag, hostList, 0)    // :148
runAll(igor.ExternalCmds.PowerOff, hostList, 0)              // :160
runAll(igor.ExternalCmds.PowerOn, hostList, 0)               // :178
```

The third argument is the per-command timeout. `0` means no deadline
(`external.go:39-45`):

```go
if timeout > 0 {
    ctx, cancel = context.WithTimeout(ctx, timeout)
} else {
    // still derive a cancellable ctx to keep symmetry (caller cancels if they want)
    ctx, cancel = context.WithCancel(ctx)
}
```

Nothing cancels that context until the command has already returned, so
`cmd.CombinedOutput()` blocks for as long as the external process runs.

## Cause

The timeout parameter was introduced in the v2.3.0 external-command rework and is used
correctly elsewhere — `probe_power.go:28` passes a real 2s bound for the *status* probe:

```go
outputMap, err := runAllCapture(igor.ExternalCmds.PowerStatus, hostNames, c.Timeout)
```

`doPowerHosts` is the only caller that passes `0`. The asymmetry is an oversight rather
than a deliberate choice: the two paths invoke the same tool against the same BMCs through
the same `DefaultRunner`.

Two multipliers apply, both from `DefaultRunner` (`runner.go:23-30`):

- `externalCmds.commandRetries` becomes `attempts = 1 + retries`, with a
  `time.Sleep(time.Second)` between attempts (`runner.go:95-105`).
- `externalCmds.concurrencyLimit` caps parallelism and **defaults to 1**
  (`config.go:712-715`), so without explicit configuration a whole reservation's worth of
  nodes is processed serially.

When the configured tool is `ipmitool`, the cycle path takes the two-pass branch
(`host_power.go:127-131`) — a full power-off sweep, then fallthrough to a full power-on
sweep — so every node is contacted twice per cycle.

The calls are made while `dbAccess` is held:

- `installReservations` holds the mutex (`scheduling.go:505`) and calls `doPowerHosts`
  at `scheduling.go:563`, inside an open `performDbTx`.
- `doDeleteRes` calls `powerOffResNodes` at `reservation_delete.go:156`, reached from
  `closeoutReservations`, which holds the mutex (`scheduling.go:283`).
- `startMaintenance` calls it at `scheduling.go:413`, reached from
  `reservation_update.go:186` and `reservation_delete.go:198`, both under the mutex.

Note that `handlePowerHosts` (`host_handlers.go:298`) takes **no** lock, so an operator-issued
`igor power` is unaffected by the mutex and can be used to test the IPMI path in isolation
while the server is wedged.

## Reproduction

Reaching the path needs only a reservation that starts or ends on a deployment with power
commands configured — the ordinary case.

The unbounded property follows directly from `external.go:39-45` and is visible with any
command that outlives the caller's patience; substituting `sleep 600` for the configured
power command demonstrates it without special hardware.

**Severity of consequence is bounded in practice, and this was measured rather than
assumed.** IPMI over `lanplus` is UDP, and `ipmitool` applies its own retry and timeout
policy, so it terminates on its own — typically in tens of seconds against an unreachable
BMC. Arithmetic for a 275-node cluster with `concurrencyLimit: 3` and `commandRetries: 1`
(attempts = 2) on a 50-node reservation cycle:

| Case | Estimate |
|---|---|
| Healthy, ~1s per call | 2 × 50 / 3 ≈ 34 slots ≈ **35s** |
| One wedged BMC (~10-20s per attempt, ×2 attempts, +1s sleep) | ≈ **90s** for the pair of sweeps |

So this produces stalls measured in minutes, not a permanent hang. That distinction
matters for diagnosis: a write outage that never clears without a restart is **not**
explained by this bug alone, and points at [BUG-008](BUG-008.md) instead.

## Impact

For the duration of the external command, every write operation server-wide blocks, and
automatic reservation cleanup stalls. Reads are unaffected, because read handlers take no
lock.

Multi-minute freezes during reservation start and teardown on large reservations, with no
log output at `info` until the command returns. `doPowerHosts` does log at Info
*immediately before* shelling out (`host_power.go:95`), so the last line in the log before
a freeze of this kind is:

```
running power operation 'cycle'/'off' on node(s) [...]
```

That line is a useful discriminator when triaging a hang.

## Suggested resolution

1. Pass a configured timeout at all four call sites instead of `0`. Add an
   `externalCmds.commandTimeout` key with a sane default; the probe's 2s is right for
   `status` but power state changes need more headroom.
2. Reconsider `concurrencyLimit`'s default of 1. At 275 nodes it makes every sweep serial.
3. Move power operations out from under `dbAccess` and outside the GORM transaction. This
   is the same structural fix as [BUG-008](BUG-008.md) item 3 and is what actually removes
   the class.

## Relationships

The relationship to [BUG-008](BUG-008.md) is worth stating precisely, because the two are
easily conflated during triage. Both are unbounded external calls under the same mutex,
and both are fixed the same structural way — but only BUG-008 can hang *permanently*.
This one always terminates eventually. A wedge that survives until the process is killed
is BUG-008's signature, not this one's.

[BUG-012](BUG-012.md) is a different blocking mechanism (an unbuffered channel send) whose
duration happens to be set by the power-status probe, so tuning the knobs named above
shortens both.
