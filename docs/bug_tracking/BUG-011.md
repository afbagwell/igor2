# BUG-011 — `findBestSolution` panics on index out of range with two or more restricted host policies

**Status:** open · **Component:** core · **Severity:** high
**Found:** 2026-07-30 · **Version:** v2.3.2

Index: [bug_tracker.md](bug_tracker.md)

---

## Location

`internal/app/igor-server/scheduling.go:130-273`, `findBestSolution`. Two distinct index
panics:

```go
cbList := make([][]ReservationTimeSlot, len(validOpenSlots))
cbList[0] = append(cbList[0], validOpenSlots[0])          // :189-190  panics when validOpenSlots is empty
```

```go
} else {
    llc := lessCapacity[0]                                 // :253      panics when lessCapacity is empty
    assigned = append(assigned, llc)
    stillNeeded -= len(cbList[llc])
}
```

## Cause

When the requesting user has access to more than one non-default host policy,
`withRestrictedHosts` is true and the function picks a single `closestPolicy`
(`:139-159`). If that one policy cannot cover the request on its own, the remainder is
taken from the default policy's slots:

```go
if len(validOpenSlotMap[closestPolicy]) <= numHostsReq {
    for i, s := range validOpenSlotMap[closestPolicy] {
        hostNameList[i] = s.Hostname
    }
    if len(validOpenSlotMap[closestPolicy]) == numHostsReq {
        return hostNameList
    }
    // we need more nodes - use default policy nodes
    validOpenSlots = validOpenSlotMap[DefaultPolicyName]
}
```

The caller's guard in `scheduleHostsByAvailability` (`:110-113`) checks only the **sum**
across all policies:

```go
if totalHostAvail < numHostsReq {
    return nil, http.StatusConflict, ...
}
```

With two or more restricted policies, that sum can be satisfied by the restricted policies
between them while the default pool holds fewer slots than the shortfall — or none at all,
or no entry in the map. `validOpenSlots` is then shorter than `stillNeeded`, and:

- if it is empty, `make(...)` produces a zero-length `cbList` and `cbList[0]` panics;
- if it is non-empty but too short, the assignment loop exhausts every non-empty block,
  leaves `stillNeeded > 0`, finds both `moreCapacity` and `lessCapacity` empty on the next
  pass, and `lessCapacity[0]` panics.

**With exactly one restricted policy this cannot happen.** `stillNeeded` is then
`numHostsReq - len(A)`, and the guard already ensures `len(A) + len(D) >= numHostsReq`,
so `len(D) >= stillNeeded` always holds. Two or more accessible non-default policies is
the precondition.

Note that gaps in node numbering are **not** involved. That was checked explicitly (see
below) and the contiguous-block logic handles them correctly.

## Reproduction

Both panics were reproduced with inputs that satisfy the caller's own
`totalHostAvail >= numHostsReq` guard, so `scheduleHostsByAvailability` would pass them
straight through to `findBestSolution`:

```
=== RUN   TestScratchTwoPoliciesDefaultEmpty      # policyA=10, policyB=10, default=0, need=15
    PANIC: runtime error: index out of range [0] with length 0
=== RUN   TestScratchTwoPoliciesDefaultShort      # policyA=10, policyB=10, default=3,  need=20
    PANIC: runtime error: index out of range [0] with length 0
```

Reaching it from the outside requires an administrator to have created two or more host
policies whose access groups the requesting user belongs to, and a reservation request
larger than any single one of them can satisfy while the default pool is short. Creating
host policies is ordinary administrator configuration (`igor policy create`), and the
request is an ordinary `igor res create -n <count>`.

Gap handling was tested separately and is correct — 70 nodes with dead nodes removed at
10-12, 30 and 45-49, requesting both all 61 survivors and 50 of 61, returned correct and
complete host lists with no blanks and no hang:

```
=== RUN   TestScratchGapsAllAvailable
    gaps-all: returned 61 names (0 blank)     --- PASS
=== RUN   TestScratchGaps50of61
    gaps-50of61: returned 50 names (0 blank)  --- PASS
```

**Not reproduced against a running server.** The panic is demonstrated at the function
level with caller-legal inputs; the end-to-end path from `igor res create` has been traced
through the source. The instance this was investigated on has exactly one restricted
policy, which is why it is not the cause of the outage under investigation there.

## Impact

On its own: the reservation create request fails. The client receives no error body and a
dropped connection rather than a 500, because of [BUG-014](BUG-014.md).

Combined with [BUG-010](BUG-010.md), which is in the calling handler: the panic unwinds
past a non-deferred `dbAccess.Unlock()`, permanently leaking the global write mutex and
taking every write operation server-wide down until the process is killed. That composite
is what makes this high severity rather than medium.

## Suggested resolution

Two independent fixes:

1. **Guard the indices.** `findBestSolution` should return an error rather than panic when
   the slot list it has been handed cannot satisfy `stillNeeded`. It currently has no error
   return; adding one means touching `scheduleHostsByAvailability` at `:115`.
2. **Fix the underlying selection logic**, which is the real defect. Restricting the
   remainder to `DefaultPolicyName` is wrong when several restricted policies are available
   — the function should be able to draw from any combination of accessible policies. The
   `closestPolicy` selection loop at `:139-159` also has questionable comparisons
   (`closeness > closestSize && closeness < 0` cannot hold when `closestSize` starts at
   `math.MaxInt32` and is only ever lowered) and deserves review alongside.

Both scratch tests above should be promoted to permanent cases in `scheduling_test.go`,
which currently exercises only single-policy scenarios (`TestNoContiguousBlocks`,
`TestChooseSmallerContiguousBlock`).
