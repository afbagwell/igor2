# BUG-008 — Arista VLAN RPC has no timeout and blocks the global write mutex indefinitely

**Status:** open · **Component:** core · **Severity:** high
**Found:** 2026-07-30 · **Version:** v2.3.2

Index: [bug_tracker.md](bug_tracker.md)

---

## Location

`internal/app/igor-server/network_arista.go:62-90`, in `aristaJSONRPC`:

```go
t := &http.Transport{
    TLSClientConfig:     &tls.Config{InsecureSkipVerify: true},
    TLSHandshakeTimeout: time.Second * 5,
    MaxIdleConns:        100,
    MaxConnsPerHost:     100,
    MaxIdleConnsPerHost: 100,
}

client := &http.Client{
    Transport: t,
    //Timeout: time.Second * 30,
}

path := fmt.Sprintf("http://%s:%s@%s", user, password, URL)
req, err := http.NewRequest("POST", path, strings.NewReader(string(data)))
...
resp, err := client.Do(req)
```

## Cause

The client has no completion deadline of any kind:

- `Timeout` is commented out.
- `http.NewRequest` is used rather than `http.NewRequestWithContext`, so there is no
  request context to cancel.
- `TLSHandshakeTimeout` is the only bound present, and it never applies — the URL is
  built with the `http://` scheme (`network_arista.go:77`), so no TLS handshake occurs.

A peer that completes the TCP handshake and then never sends a response leaves
`client.Do` blocked forever. TCP keepalive does not help: it detects a *dead* peer, not a
live one that is simply silent.

Two aggravating factors in the same function:

1. **A new `Transport` is constructed on every call.** Connections are therefore never
   reused. `aristaSet` and `aristaClear` call `aristaJSONRPC` **once per host,
   sequentially** (`network_arista.go:109-128` and `133-154`), so a 50-node reservation
   opens 50 separate TCP connections to the switch management plane in quick succession.
2. **The abandoned `Transport` is never closed.** A hand-constructed `http.Transport`
   leaves `IdleConnTimeout` at its zero value, meaning idle connections never expire, and
   `CloseIdleConnections` is never called. The connection survives GC because its
   `readLoop` goroutine roots the `Transport`. It is reclaimed only when the *switch*
   closes it, at whatever its own HTTP keepalive timeout happens to be.

The blocking call is made while the global write mutex is held, and from inside an open
GORM transaction:

- `installReservations` takes `dbAccess` (`scheduling.go:505`), opens `performDbTx`
  (`scheduling.go:523`), and calls `networkSet` at `scheduling.go:546`.
- `doDeleteRes` calls `networkClear` at `reservation_delete.go:142`, reached from
  `closeoutReservations`, which holds `dbAccess` (`scheduling.go:283`).

Because every state-changing handler takes that same mutex (`database.go:21`), one stalled
switch RPC stops all writes server-wide. Read handlers take no lock — `handleReadReservations`
(`reservation_handlers.go:57`) and `show_handler.go` — so reads continue to work normally,
which makes the failure look like a database problem rather than a network one.

## Reproduction

The client's blocking property was demonstrated directly. The construction above was
reproduced verbatim against an `httptest` server that accepts the connection, reads the
request and never responds:

```
=== RUN   TestScratchAristaClientBlocksForever
    as-shipped client (no Timeout, no ctx): STILL BLOCKED after 10s
--- PASS (10.01s)
=== RUN   TestScratchAristaClientWithTimeoutReturns
    same client WITH Timeout=2s: returned in 2.001s with err=Post "http://127.0.0.1:42319":
      context deadline exceeded (Client.Timeout exceeded while awaiting headers)
--- PASS (2.00s)
```

The 10s bound is the test's observation window, not a limit on the block. Adding
`Timeout` to the otherwise identical client is sufficient to bound it.

Reaching the code path requires only `vlan.network: arista` and an ordinary reservation
that starts, is extended, or ends. No privileged operation and no unusual input is
involved.

**Not yet reproduced end to end against a live switch.** What is established is that the
client cannot time out and that reservation create/install/delete reach it while holding
`dbAccess`. Whether a production Arista management plane actually stalls under a
50-connection burst — as opposed to refusing the connection outright, which would return
an error rather than hang — is the open question. See the investigation runbook for the
socket-count measurements that would confirm it.

## Impact

Every write operation server-wide hangs indefinitely: reservation create, delete, update,
extend, group and user edits, host changes. Reads keep working, so the server appears
healthy to `igor show` and to monitoring.

Automatic reservation cleanup stops, because `closeoutReservations` is itself just another
waiter on `dbAccess` (`scheduling.go:283`). Expired reservations continue to hold their
nodes, and their owners are not notified.

Recovery requires killing the process. A graceful restart does not work — see
[BUG-013](BUG-013.md) — so the service must be SIGKILLed by the systemd stop timeout.

Nothing is written to the log at `info`. `aristaJSONRPC`'s only pre-call log line is
`logger.Debug()` (`network_arista.go:51`), and the handler's own Info line is emitted
after the work returns (`reservation_handlers.go:51`), which never happens.

## Suggested resolution

Three changes, all in `aristaJSONRPC`:

1. Set an overall `Timeout` on the client, and build the request with
   `http.NewRequestWithContext` so callers can cancel a whole batch. Make the value
   configurable rather than hard-coding 30s.
2. Hoist the `Transport` to package scope so connections are reused across the per-host
   loop, or call `CloseIdleConnections` when done. One connection per reservation instead
   of one per host also removes the burst.
3. Longer term, move `networkSet`/`networkClear` out from under `dbAccess` and outside the
   GORM transaction. Holding a global write lock and an open SQLite write transaction
   across a network round trip to a switch is the structural defect; the missing timeout
   is what makes it visible. This is the shared fix for [BUG-009](BUG-009.md).

A regression test can use the stalling `httptest` server shown above and assert that
`aristaJSONRPC` returns an error within the configured bound.
