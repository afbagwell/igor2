# BUG-017 — Image registration deadlocks against the initrd worker, wedging all writes permanently

**Status:** open · **Component:** core · **Severity:** high
**Found:** 2026-08-03 · **Version:** v2.3.2

Index: [bug_tracker.md](bug_tracker.md)

---

## Location

The producer, `processImage` (`distro_image_create.go:167-179`), hands the new row to the
initrd worker **from inside the locked region**:

```go
lockedDbWrite(func() {
    if err = dbCreateImage(image, tx); err != nil { ... }

    enqueueInitrdJob(image)          // distro_image_create.go:174
    ...
})
```

`enqueueInitrdJob` (`server.go:283-290`) is a thin wrapper over a **blocking** send:

```go
func (q *InitrdJobQueue) Enqueue(job InitrdJob) {
    q.queue <- job                   // distro_initrd_info.go:60
}
```

The channel has a fixed buffer of 100 and exactly one drain:

```go
queue: make(chan InitrdJob, 100)     // distro_initrd_info.go:45

func (q *InitrdJobQueue) Start() {
    go func() {
        for job := range q.queue {   // distro_initrd_info.go:52 — a single worker
            q.processInitrdJob(job)
        }
    }()
}
```

And that sole drain needs the same mutex the producer is holding:

```go
func (q *InitrdJobQueue) processInitrdJob(job InitrdJob) {
    ...
    initrdInfo := parseInitrdInfo(imageInitrdPath)   // slow: xz decompress + full cpio scan
    ...
    lockedDbWrite(func() {                           // distro_initrd_info.go:150
        saveErr = performDbTx(...)                   // UPDATE initrd_info
    })
}
```

## Cause

A classic circular wait, in the same class as the `resNotifyChan` inversion recorded under
"Not tracked as bugs" — but this one is reachable, for the reason given below.

* `processImage` holds `dbAccess` and blocks sending to a full queue.
* The only goroutine that can drain that queue is the worker, and it is blocked acquiring
  `dbAccess`.

Neither can proceed, and nothing times out. `sync.Mutex` has no owner tracking and the send
has no `select`/`default`, so the state is permanent.

The window is not narrow, because the worker is only vulnerable **between** its dequeue and
its `lockedDbWrite` — and that gap is exactly `parseInitrdInfo`, which reads the initrd off
disk, xz-decompresses it into memory (`processCpioArchive` does `io.Copy` of the whole
archive into a `bytes.Buffer`) and then walks the cpio archive once per candidate release
file: up to 12 full passes over the decompressed image. That is seconds of work per job on
a real initrd.

### Why the queue reaches 100

This is what separates it from the rejected `resNotifyChan` finding, where filling the
buffer needed an implausible burst. Here, filling it is the **designed startup behaviour**:

`EnqueuePendingJobs` (`distro_initrd_info.go:66-120`) walks every image with
`initrd_info = ""` in batches of 25 and pushes each one, with no bound on the total:

```go
for i := range pendingImages {
    q.Enqueue(InitrdJob{Image: &pendingImages[i]})   // :114
}
```

It is started concurrently with the worker at boot (`server.go:153-154`):

```go
initrdQueue.Start()
go initrdQueue.EnqueuePendingJobs()
```

So on any instance with more than 100 unprocessed images, the buffer sits at 100 for the
whole backlog fill — `EnqueuePendingJobs` blocks on its own send, refilling each slot the
instant the worker frees it. Every image registration during that window meets a full queue.

Two things make that backlog easy to have:

1. **First start after upgrade.** Every pre-existing image has `initrd_info = ""`, so the
   entire image library is enqueued at once.
2. **`NewInitrdJobQueue` resets `pending` back to `""` on every start**
   (`distro_initrd_info.go:33-38`). A restart part-way through a fill re-queues everything
   that was in flight, so an instance that hits this once will hit it again on each restart.

A second, slower route needs no backlog at all: a bulk import that registers images faster
than the worker retires them will walk the buffer up to 100 on its own.

## Reproduction

Demonstrated with the real `InitrdJobQueue`, the real blocking `Enqueue`, and the real
`lockedDbWrite`, driving the same call ordering the two production paths use. The buffer was
reduced from 100 to 4 to reach the full state quickly; nothing else was substituted, and the
harness is reproduced at the end of this document.

```
=== RUN   TestReproInitrdQueueDeadlock
    step 1: queue filled to capacity 4
    step 2: worker dequeued one job and is in parseInitrdInfo (slow xz/cpio work)
    step 3: backlog refilled the free slot; queue full again
    step 4: producer holds dbAccess and is blocked on a full queue
    step 5: worker released from parse, now wants dbAccess
    DEADLOCK CONFIRMED: after 3s neither the producer nor the worker progressed
      producer: holds dbAccess, blocked sending to a full queue
      worker:   holds the only drain, blocked acquiring dbAccess
    an unrelated write handler also cannot acquire dbAccess: writes are wedged server-wide
--- PASS: TestReproInitrdQueueDeadlock (5.10s)
```

The last line is the part that matters operationally: a third, entirely unrelated
`lockedDbWrite` — standing in for any write handler — also never acquires the mutex.

**Ordering matters, and rules out the obvious objection.** A receive on a full buffered
channel wakes a blocked sender immediately, so the deadlock does *not* occur if the worker
is sitting at its `range`. It requires the worker to have already dequeued and to be inside
`parseInitrdInfo` when the producer takes the mutex. Step 2 of the harness establishes
exactly that state.

**Not reproduced against a running server.** The 100-image backlog and the concurrent
registration have not been staged on a live instance; the deadlock cycle itself is
demonstrated above against the real primitives.

## Impact

Every database write in the process stops, permanently. Reads take no lock and keep working,
so the server looks healthy: it answers `igor show`, serves the web UI, and returns 200s,
while every create, edit, delete and the scheduler's own `closeoutReservations` and
`installReservations` sweeps block forever.

Reservations therefore neither start nor expire for as long as the process lives, and
because [BUG-013](BUG-013.md)'s bounded shutdown only covers in-flight requests, clearing it
means killing the process.

The trigger is an ordinary authenticated user action. `api.ImageRegister` is behind
`hcAuthChain` with no admin gate (`routes.go:369-373`), so any user who can register a
distro image can wedge the server, without needing to do anything unusual — just upload one
image while the startup backlog is draining.

This is the failure mode `lockedDbWrite`'s own doc comment warns about, arrived at from the
other direction: not a leaked mutex, but one held across a blocking hand-off to a goroutine
that needs it back.

## Suggested resolution

1. **Move the hand-off out of the locked region.** `enqueueInitrdJob` needs the row to be
   committed, not the mutex to be held. Ending the `lockedDbWrite` before the enqueue
   removes the cycle outright and is the smallest correct change.

2. **Make the send non-blocking**, so a saturated queue degrades instead of deadlocking:

   ```go
   select {
   case q.queue <- job:
   default:
       logger.Warn().Msgf("initrd queue full; image %s left unprocessed", job.Image.ImageID)
   }
   ```

   Dropping is safe *only* because `EnqueuePendingJobs` re-finds anything left at
   `initrd_info = ""` on the next start — but note that it would then need to not have
   marked the row `pending`, or the row must be reset on the drop path. Getting that
   backwards silently strands images at `pending` forever.

3. **Do not hold `dbAccess` across any channel send.** This is the third instance of the
   same shape (see Relationships). A one-off fix here leaves the pattern available to the
   next person; the class deserves a rule.

Fixing (1) alone closes this bug. (2) is defence in depth for the bulk-import route.

already flags that it is "worth revisiting if a future notify type does unbounded work", and
`parseInitrdInfo` is precisely that consumer, on a different channel.

## Appendix — reproduction harness

Placed in `internal/app/igor-server/` and run with
`go test ./internal/app/igor-server/ -run TestReproInitrdQueueDeadlock -v`. Not committed:
it asserts the presence of the defect, so it would invert on the fix. A proper regression
test — asserting the registration completes while the queue is full — belongs with the fix.

```go
func TestReproInitrdQueueDeadlock(t *testing.T) {
	const capacity = 4 // stands in for the real 100

	q := &InitrdJobQueue{queue: make(chan InitrdJob, capacity)}

	// Step 1: backlog fills the buffer (EnqueuePendingJobs at startup).
	for i := 0; i < capacity; i++ {
		q.Enqueue(InitrdJob{Image: &DistroImage{ImageID: "backlog"}})
	}

	parked := make(chan struct{})
	releaseParse := make(chan struct{})
	workerSaved := make(chan struct{})

	// The worker: dequeue, do the slow parse, then take dbAccess to save.
	go func() {
		<-q.queue      // dequeue leaves one free slot
		close(parked)  // now "inside parseInitrdInfo"
		<-releaseParse // held here so the test controls the interleaving
		lockedDbWrite(func() {
			// stands in for the initrd_info UPDATE
		})
		close(workerSaved)
	}()

	<-parked

	// Step 3: the backlog fill immediately reclaims the free slot. Buffer is full again.
	q.Enqueue(InitrdJob{Image: &DistroImage{ImageID: "backlog-refill"}})

	// Step 4: a user registers an image. processImage takes dbAccess, writes the row,
	// then enqueues -- while still holding the mutex.
	producerHasLock := make(chan struct{})
	producerDone := make(chan struct{})
	go func() {
		lockedDbWrite(func() {
			close(producerHasLock)
			q.Enqueue(InitrdJob{Image: &DistroImage{ImageID: "user-upload"}})
		})
		close(producerDone)
	}()

	<-producerHasLock
	time.Sleep(100 * time.Millisecond) // let the producer reach the blocking send

	// Step 5: the worker finishes parsing and now needs dbAccess.
	close(releaseParse)

	select {
	case <-producerDone:
		t.Fatal("NO DEADLOCK: the producer completed")
	case <-workerSaved:
		t.Fatal("NO DEADLOCK: the worker completed")
	case <-time.After(3 * time.Second):
		t.Log("DEADLOCK CONFIRMED")
	}

	// Prove the mutex is wedged for everything else, which is the server-wide impact.
	thirdWriter := make(chan struct{})
	go func() {
		lockedDbWrite(func() {})
		close(thirdWriter)
	}()
	select {
	case <-thirdWriter:
		t.Fatal("an unrelated writer acquired dbAccess; it was not wedged")
	case <-time.After(2 * time.Second):
		t.Log("writes are wedged server-wide")
	}
}
```
