# BUG-006 — Removing a group owner panics the server on a nil template

**Status:** fixed in `PENDING` · **Component:** core · **Severity:** high
**Found:** 2026-07-30 · **Version:** v2.3.2

Index: [bug_tracker.md](bug_tracker.md)

---

## Location

`internal/app/igor-server/notify.go:435-437`, the `EmailGroupRmvOwner` case of
`processGroupNotifyEvent`:

```go
case EmailGroupRmvOwner:
    subj = "igor: you have been removed from owner list of group '" + msg.Group.Name + "'"
    t = tMap[EmailGroupRmvOwner]
    addEmailToList(&toList, msg.Member.Email)
```

## Cause

`initNotify` never populates `tMap[EmailGroupRmvOwner]`. It builds an entry for every
other dispatched type, including its sibling `EmailGroupAddOwner`
(`notify.go:89-94`), but there is no `EmailGroupRmvOwner` entry and no
`NotifyGroupOwnerRemoveTemplate` constant anywhere in the file.

Reading an absent key from `map[int]*template.Template` yields a nil `*template.Template`.
That nil is passed to `sendEmail`, which calls `t.Execute(&body, info)` on it.
`html/template.(*Template).Execute` does not nil-check its receiver — it calls
`t.escape()`, which dereferences `t.nameSpace`:

```
panic: runtime error: invalid memory address or nil pointer dereference
html/template.(*Template).escape(0x0)  .../html/template/template.go:97
html/template.(*Template).Execute(0x0, ...)  .../html/template/template.go:121
```

(Confirmed by executing a nil template from an absent map key on this toolchain.)

`processGroupNotifyEvent` runs on the `notificationManager` goroutine
(`server.go:319`), and there is no `recover()` anywhere in the `igorserver` package, so
the panic is not contained — it takes the whole igor-server process down.

## Reproduction

Remove an owner from a group, e.g. `igor group edit <name> -r <owner>`. That reaches
`group_update.go:281-287`, which builds the `EmailGroupRmvOwner` event and pushes it onto
the notify channel. The panic follows as soon as the notification manager picks it up.

Two preconditions, both ordinary: `igor.Email.SmtpServer` must be configured (otherwise
`makeGroupNotifyEvent` returns nil and no event is queued), and the removed owner must
have an email address on file (otherwise the recipient guard in `sendEmail` returns
before the template is executed). On a deployment with email enabled and real user
accounts, both hold.

`TestGroupRmvOwnerRendersAndSends` in `notify_test.go` reproduces it. Against the unfixed
code the template lookup comes back nil:

```
Error:    Expected value not to be nil.
Messages: EmailGroupRmvOwner must have a template
```

Not reproduced against a running instance — the panic mechanism is confirmed directly
(executing a nil template from an absent map key), but the end-to-end path from
`igor group edit -r` has been traced through the source rather than observed.

## Impact

Server crash — full loss of availability for every user — triggered by a routine,
non-privileged group edit. Reservations already installed on hardware keep running, but
the scheduler, the API and the CLI are all down until the process is restarted, and the
same command crashes it again.

## Resolution

`NotifyGroupOwnerRemoveTemplate` was added and registered in `initNotify`, mirroring the
`EmailGroupAddOwner` block:

```
You have been removed from the owner list of the group '{{.Group.Name}}'.
```

Paired with a nil-template guard in `sendEmail`, which now returns a typed
`MissingEmailTemplateError` instead of letting `Execute` panic. That converts any future
unregistered type from a server crash into one undelivered email and a logged error.

A startup assertion enumerating every dispatchable type was considered and deliberately
not added: the list would itself be a second thing to keep in step, and the nil guard
already removes the catastrophic outcome. What *was* done instead is structural —
see [BUG-007](BUG-007.md) — making template registration independent of configuration, so
the set of registered types is now a static fact rather than something that varies at
runtime.

Covered by `TestGroupRmvOwnerRendersAndSends` and `TestSendEmailRejectsNilTemplate` in
`internal/app/igor-server/notify_test.go`. Both were confirmed to fail against the
original code, the second by panicking with the trace shown above.

## Relationships

| Relationship | Bug | Note |

| related to | [BUG-007](BUG-007.md) | Same failure mechanism — a nil template reaching `Execute` — from a different cause. Isolated; fixed together but either could have been done first. |

[BUG-007](BUG-007.md) was found while fixing this one and shares its *mechanism*, not its
*cause*. Here the template was never written at all, so the gap exists under every
configuration. There, the templates exist but are registered only when
`Email.ResNotifyOn` is true, while the guard meant to keep dispatch in step tested the
wrong constant range and never fired. Fixing either would have left the other panicking.
The `sendEmail` nil check closes the shared mechanism for both.

No relationship to [BUG-004](BUG-004.md) or [BUG-005](BUG-005.md) beyond sharing the
file. Those two concern recipient assembly; this one is a missing template registration,
and neither their causes nor their fixes touch it. The BUG-004 fix was checked against
this path specifically and changes nothing about it: the panic occurs when the removed
owner *has* an address, which is exactly the case where the recipient guard — old or new
— lets the message through to `t.Execute`.
