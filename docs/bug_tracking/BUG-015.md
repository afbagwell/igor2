# BUG-015 — `igor sync arista` panics on any switch error response

**Status:** open · **Component:** core · **Severity:** medium
**Found:** 2026-07-31 · **Version:** v2.3.2

Index: [bug_tracker.md](bug_tracker.md)

---

## Location

`internal/app/igor-server/network_arista.go:159-181`, `aristaVlan`. Four unchecked type
assertions on switch-controlled data:

```go
res, err := aristaJSONRPC(igor.Vlan.NetworkUser, igor.Vlan.NetworkPassword, igor.Vlan.NetworkURL, commands)
...
res2 := res["result"].([]interface{})                                            // :169
res3 := res2[0].(map[string]interface{})                                         // :170
data := res3["vlans"].(map[string]interface{})                                   // :171
...
inter := value.(map[string]interface{})["interfaces"].(map[string]interface{})   // :175
```

## Cause

`aristaJSONRPC` returns early on a transport error, and on a body that will not unmarshal.
It does **not** distinguish a JSON-RPC *success* response from a JSON-RPC *error*
response — both are valid JSON and both unmarshal cleanly into `map[string]interface{}`.

An eAPI error response carries an `"error"` object and **no `"result"` key**:

```json
{"jsonrpc":"2.0","id":1,"error":{"code":1002,
 "message":"CLI command 1 of 1 'show vlan 100-200' failed: invalid command",
 "data":[{"errors":["No VLANs configured"]}]}}
```

Reading an absent key from a `map[string]interface{}` yields a nil `interface{}`, and
`nil.([]interface{})` is a failed type assertion, which panics rather than returning the
comma-ok zero value.

The remaining three assertions have the same shape and fail on any schema the code does
not expect — `res2[0]` also panics on an empty result array.

Note the command being sent (`:161`):

```go
commands := []string{fmt.Sprintf("show vlan %v-%v", igor.Vlan.RangeMin, igor.Vlan.RangeMax)}
```

If no VLANs are currently configured within `rangeMin`-`rangeMax` — the ordinary state of
a cluster with no active reservations — the switch returns an error rather than an empty
result. That makes the panic reachable through routine operation, not just misconfiguration.

## Reproduction

The failing assertion was reproduced directly, feeding a real eAPI error response through
the same `json.Unmarshal` and assertion the code performs:

```
unmarshal OK; keys present:
  "jsonrpc"
  "id"
  "error"

aristaVlan line 169 -> PANIC: interface conversion: interface {} is nil, not []interface {}
```

Reaching it needs an elevated admin to run `igor sync arista` at a moment when the switch
returns an error for the `show vlan` query. Both halves are ordinary: `igor sync arista` is
a documented administrative command, and an out-of-range or empty VLAN window is a normal
cluster state.

**Not reproduced end to end against a live switch.** The panic mechanism is demonstrated
with a genuine error-response payload; the path from `igor sync arista` to `aristaVlan` is
traced through the source (`sync_handler.go:126` → `network.go:88` → `network_arista.go:159`).

## Impact

Bounded, and notably *not* an availability problem.

`syncHandler` (`sync_handler.go:21`) takes **no** `dbAccess` lock — it calls `runSync`
directly. So unlike [BUG-008](BUG-008.md) and [BUG-009](BUG-009.md), a panic here cannot
wedge the global write mutex. `httprouter` recovers it, the server stays up, and no other
request is affected.

What the operator sees is a dropped connection rather than a diagnosis. Because of
[BUG-014](BUG-014.md), `panicHandler` re-panics before writing its 500 response, so the
CLI reports a transport error and the useful message — "the switch returned an error for
your `show vlan` query" — never reaches anyone. The admin is left unable to tell a switch
problem from an igor problem.

There is also a diagnostic cost. `igor sync arista` is the natural tool for checking
whether igor's view of VLAN state matches the switch's, which is exactly what an operator
would reach for while investigating the write hangs in [BUG-008](BUG-008.md). It fails
unhelpfully in precisely that situation.

## Suggested resolution

Use comma-ok assertions throughout and return a typed error naming what the switch
actually said:

```go
if apiErr, ok := res["error"]; ok {
    return nil, fmt.Errorf("switch returned an eAPI error: %v", apiErr)
}
resultList, ok := res["result"].([]interface{})
if !ok || len(resultList) == 0 {
    return nil, fmt.Errorf("unexpected eAPI response shape: %v", res)
}
```

Checking for `"error"` first is the important part — it converts the common case from a
panic into an actionable message.

The same treatment should be applied to the remaining assertions at `:170`, `:171` and
`:175`. A regression test can feed the error payload above through `aristaVlan` and assert
that it returns an error rather than panicking.
