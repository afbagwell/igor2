# BUG-014 — `panicHandler` re-panics, so the client never receives the 500 response

**Status:** fixed (`88a9471`) · **Component:** core · **Severity:** medium
**Found:** 2026-07-30 · **Fixed:** 2026-08-12 · **Version:** v2.3.2

Index: [bug_tracker.md](bug_tracker.md)

---

## Location

`internal/app/igor-server/handler_util.go:79-84`:

```go
func panicHandler(w http.ResponseWriter, r *http.Request, err interface{}) {
	logger.Panic().Stack().Msgf("panic intercepted - %v: %v\n%v", r.URL.Path, err, string(debug.Stack()))
	rb := common.NewResponseBody()
	rb.Message = fmt.Sprintf("server error; please notify admins : %v", err)
	makeJsonResponse(w, http.StatusInternalServerError, rb)
}
```

Registered at `routes.go:26` as `httprouter.Router.PanicHandler`.

## Cause

`logger.Panic()` is zerolog's panic *level*, which calls `panic()` after writing the event.
From `zerolog@v1.33.0/log.go:404`:

```go
func (l *Logger) Panic() *Event {
	return l.newEvent(PanicLevel, func(msg string) { panic(msg) })
}
```

and `event.go:141-152`, where the supplied function is run as a deferred call:

```go
if e.done != nil {
	defer e.done(msg)
}
if err := e.write(); err != nil {
	...
}
```

So the event is written to the log first, and then the goroutine panics again. Lines 81-83
of `panicHandler` — which build and send the 500 response — are never reached.

The second panic escapes `httprouter`'s recovery, because that recovery is the deferred
`recv` that called `panicHandler` in the first place (`httprouter/router.go:309-313`):

```go
func (r *Router) recv(w http.ResponseWriter, req *http.Request) {
	if rcv := recover(); rcv != nil {
		r.PanicHandler(w, req, rcv)
	}
}
```

A panic raised inside a deferred function during unwinding is not caught by that same
`recover()`. It propagates to `net/http`'s per-connection recovery in `conn.serve`, which
logs to `http.Server.ErrorLog` and closes the connection.

`ErrorLog` is never set on either server (`server.go:116-134`), so it defaults to the
standard library's logger, writing to stderr rather than to `igor.log`. Under systemd that
goes to the journal, in a different place from every other igor log line.

The intent was clearly to log at a severe level; `logger.Error()` would have done that
without the side effect.

## Reproduction

Any handler panic. [BUG-011](BUG-011.md) is a demonstrated reachable one.

**Reproduced end to end 2026-08-12** (this section previously read "not reproduced"), against
an `httptest` server carrying igor's own `panicHandler`:

- A handler that panics gave the client a transport error and no body at all. With the fix it
  returns `500` carrying igor's JSON `{"message": "server error; please notify admins"}`.
- Calling `panicHandler` directly re-panicked and killed the test binary outright, printing
  `panic: panic intercepted - /distros: ...`. That is the second panic escaping, observed
  rather than inferred.

The zerolog behaviour is as read from the vendored source: `defer e.done(msg)` runs after
`e.write()`, so the message reaches the log and the panic then re-raises.

## Impact

Three separate degradations, all at the moment when diagnostic information matters most:

1. **The client gets nothing useful.** Instead of a 500 with
   `server error; please notify admins : ...`, the connection is closed. `igor` reports a
   transport error, which reads to the user as a network problem rather than a server
   fault.
2. **The stack trace is split across two destinations.** The `PANIC` line and
   `debug.Stack()` go to `igor.log`; the second panic and its trace go to stderr and the
   journal. An operator reading only `igor.log` sees a truncated picture, and one reading
   only the journal sees no igor context.
3. **A second panic per incident** for no benefit, since the first was already recovered
   and reported.

It also actively hinders diagnosis of [BUG-010](BUG-010.md): the write outage that follows
a create-path panic is silent, and the one clear signal — a `PANIC` line in `igor.log` — is
easy to overlook when the accompanying stack is somewhere else and the client saw only a
dropped connection.

## Resolution

Fixed in `88a9471`.

**`logger.Error()` replaces `logger.Panic()`.** Same severity in the log, and it returns. The
`.Stack()` call went with it: it decorates an error attached via `Err()`, of which there is
none here, and `ErrorStackMarshaler` is never configured, so it was a no-op. The trace still
comes from `debug.Stack()` in the message.

**The panic value no longer goes back to the client.** This is a deliberate departure from the
suggested resolution below, which kept `server error; please notify admins : %v`. A panic
value is a raw runtime message — `index out of range [3] with length 2`, a driver error, a
filesystem path — and §4 does not permit returning those. It is logged in full alongside the
request path and the stack, so an incident remains diagnosable from `igor.log` alone.

The cost is real and worth stating: an administrator running the failing command used to see
the runtime error in their own terminal, and now sees a generic message. Correlation is by
time and path in the log. A request id echoed in the response and logged with each entry
would give that back properly; `hlog.RequestIDHandler` already exists for it. Not done here —
it adds a response header, which is a public-interface change and belongs in its own change.

**Both `http.Server` instances now set `ErrorLog`** (`server.go`) to an adapter that writes
into zerolog (`newHttpErrorLog`, `logger.go`). This was flagged below as worth doing
regardless, and it closes the split described under Impact: the igor-side panic record went
to `igor.log` while `net/http`'s account of the same event went to stderr, and under systemd
to the journal.

### Covering tests

In `internal/app/igor-server/panic_handler_test.go`. All were confirmed to fail against the
pre-fix code — the first three by the panic escaping, the last by removing an `ErrorLog`.

### What this does not fix

Nothing about *why* handlers panic. [BUG-011](BUG-011.md) remains an open, reachable panic
source; it will now produce a logged 500 instead of a dropped connection, which is the point.

### Original suggested resolution


Use a level that does not terminate the goroutine:

```go
func panicHandler(w http.ResponseWriter, r *http.Request, err interface{}) {
	logger.Error().Stack().Msgf("panic intercepted - %v: %v\n%v", r.URL.Path, err, string(debug.Stack()))
	rb := common.NewResponseBody()
	rb.Message = fmt.Sprintf("server error; please notify admins : %v", err)
	makeJsonResponse(w, http.StatusInternalServerError, rb)
}
```

Separately, set `ErrorLog` on both `http.Server` instances to an adapter that writes into
the zerolog logger, so anything `net/http` reports lands in `igor.log` with everything
else. That is worth doing regardless of this fix — it is currently the only route by which
server-level errors escape the configured log destination.

Note that `logger.Fatal()` would be worse, not better: it calls `os.Exit(1)`.

A regression test can assert that `panicHandler` returns normally and writes a 500 body,
which fails against the current code by panicking.
