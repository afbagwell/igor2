# BUG-007 — With `resNotifyOn: false`, every reservation start and expiry panics the server

**Status:** fixed in `PENDING` · **Component:** core · **Severity:** high
**Found:** 2026-07-30 · **Version:** v2.3.2

Index: [bug_tracker.md](bug_tracker.md)

---

## Location

Two sites that disagree about when reservation-time emails exist.

**1. Conditional registration** — `internal/app/igor-server/notify.go:146-176` in `initNotify`:

```go
// if reservation notification is turned on, load these
if *igor.Email.ResNotifyOn {
    ...
    tMap[EmailResExpire] = t
    tMap[EmailResWarn] = t
    tMap[EmailResStart] = t
    tMap[EmailResFinalWarn] = t
}
```

**2. The guard meant to match it** — `notify.go:528-532` in `processResNotifyEvent`:

```go
// filter out reservation time emails of flag is turned off (extend, expire, time left...)
if !*igor.Email.ResNotifyOn && 1200 <= msg.Type && msg.Type < 1300 {
```

## Cause

The guard tests the wrong constant block. The reservation-time types are the **1100**
block; `1200-1299` is the **account** block:

```
EmailResStart=1100  EmailResExtend=1101  EmailResExpire=1102  EmailResWarn=1103  EmailResFinalWarn=1104
EmailAcctCreated=1200  EmailPasswordReset=1201  EmailAcctRemovedIssue=1202
```

Account emails are handled by `processAcctNotifyEvent` and never reach
`processResNotifyEvent`, so the condition can never be true for anything that arrives
there. The guard is dead code, and has been since it was written.

So when `ResNotifyOn` is false, the four templates are absent *and* nothing filters the
events. A missing `tMap` key yields a nil `*template.Template`, and
`html/template.(*Template).Execute` does not nil-check its receiver — it panics. That
happens on the `notificationManager` goroutine, and there is no `recover()` anywhere in
the `igorserver` package, so the process dies.

Crucially, the two dispatch sites are **not** guarded by `ResNotifyOn` either:

- `scheduling.go:588` — `makeResWarnNotifyEvent(EmailResStart, ...)` on every reservation start
- `scheduling.go:324` — `makeResWarnNotifyEvent(EmailResExpire, ...)` on every reservation expiry

`makeResWarnNotifyEvent` only checks that `Email.SmtpServer` is non-empty. By contrast
`EmailResWarn` and `EmailResFinalWarn` are dispatched only from `sendExpirationWarnings`,
which *is* wrapped in `if *igor.Config.Email.ResNotifyOn` (`scheduling.go:605`) — which is
why those two never fired the panic and only start/expiry did.

## Reproduction

The triggering configuration is `email.smtpServer` set **and** `email.resNotifyOn: false`
— a documented, supported combination. `conf/igor-server.yaml:401-404` describes
`resNotifyOn` as "Determines if email notifications about reservations starting and
stopping are sent" with "Default: true".

The default is what has masked this. `config.go:611-615` sets `ResNotifyOn` to true when
it is unset, and `config.go:576-579` forces it to false when no SMTP server is configured
— in which case `makeResWarnNotifyEvent` returns nil and nothing is dispatched. Only an
operator who explicitly turns the flag off while email is enabled lands in the gap, and
that deployment then crashes the first time any reservation starts.

`TestResTimeEmailsFilteredWhenNotifyOff` in `notify_test.go` reproduces it. Against the
unfixed code the test binary dies rather than failing:

```
panic: runtime error: invalid memory address or nil pointer dereference
html/template.(*Template).escape(0x0)
html/template.(*Template).Execute(0x0, ...)
igor2/internal/app/igor-server.sendEmail(0x0, ...)
```

Not reproduced against a running instance; the trace above is from the unit test, and the
dispatch path was traced through the source.

## Impact

Server crash — total loss of the API, CLI and scheduler — on an ordinary reservation
start, on any deployment that has email enabled and reservation notifications turned off.
Nodes already provisioned keep running, but nothing can be reserved, extended or released
until the process is restarted, and the next reservation to start crashes it again.

Effectively this makes `resNotifyOn: false` an unusable setting, which is why no working
deployment can be running it.

## Resolution

- The four reservation-time templates are now registered unconditionally. What `tMap`
  contains no longer depends on configuration, which removes the coupling that produced
  the gap.
- `Email.ResNotifyOn` is honored in exactly one place, the dispatch guard, and that guard
  now names its bounds instead of hard-coding them:
  `EmailResStart <= msg.Type && msg.Type < EmailAcctCreated`. Using the constants means
  the range cannot silently drift away from the block it is meant to cover.
- `sendEmail` returns a typed `MissingEmailTemplateError` when handed a nil template
  rather than letting `Execute` panic, so any future unregistered type costs one email
  instead of the server.

**Behavior change:** `EmailResExtend` (1101) is now filtered when `resNotifyOn` is off.
It was not before — the guard never fired, and extend renders through
`tMap[EmailResEdit]`, which is always registered, so it sent successfully rather than
panicking. Suppressing it matches the intent stated in the guard's own comment, which
lists "extend" first among the emails to filter. No deployment is affected in practice,
since the configuration that changes behavior is the one that could not run at all.

Covered by `TestResTimeTemplatesRegisteredWhenNotifyOff`,
`TestResTimeEmailsFilteredWhenNotifyOff`, `TestResTimeEmailsSendWhenNotifyOn` and
`TestSendEmailRejectsNilTemplate` in `internal/app/igor-server/notify_test.go`. All four
were confirmed to fail against the original code, two of them by panicking with the trace
shown above.

## Relationships

| Relationship | Bug | Note |
|---|---|---|
| related to | [BUG-006](BUG-006.md) | Same failure mechanism — a nil template reaching `Execute` — from a different cause. Isolated; fixed together but either could have been done first. |

The shared mechanism is worth stating precisely, because the two causes are not the same
and a fix for one does nothing for the other. [BUG-006](BUG-006.md) is a template that was
never written: `EmailGroupRmvOwner` has no entry under any configuration. This bug is a
template that exists but is registered only on some configurations, paired with a guard
that was supposed to keep dispatch in step and never worked. Adding the group template
would not have prevented a reservation start from panicking, and fixing the guard would
not have helped a group owner removal.

What they do share is the reason a missing entry is catastrophic rather than merely
broken — `Template.Execute` panicking on a nil receiver, on a goroutine nothing recovers.
The `sendEmail` nil check added here closes that for both, and for any type added later.
