# BUG-013 — Graceful shutdown has no timeout, so a wedged request prevents restart

**Status:** fixed in `528e6f0`, regression fixed in `6034343` · **Component:** core · **Severity:** medium
**Found:** 2026-07-30 · **Version:** v2.3.2

Index: [bug_tracker.md](bug_tracker.md)

---

## Location

`internal/app/igor-server/server.go:197-203`:

```go
func shutdownServer(srv *http.Server, name string) {
	if err := srv.Shutdown(context.Background()); err != nil {
		logger.Error().Msgf("error shutting down %s: %v", name, err)
	} else {
		logger.Info().Msgf("%s closed", name)
	}
}
```

and `server.go:169`:

```go
wg.Wait()
```

## Cause

`http.Server.Shutdown` returns when all active connections have become idle, or when the
supplied context is cancelled. `context.Background()` is never cancelled, so `Shutdown`
waits indefinitely. Any in-flight request that never completes — one blocked on
`dbAccess`, or on an untimed external call — keeps its connection active and keeps
`Shutdown` blocked.

`runServer` then blocks on `wg.Wait()`, which cannot return either: `reservationManager`
only observes `shutdownChan` between ticks (`server.go:276-297`), and if it is parked in
`dbAccess.Lock()` inside `closeoutReservations` (`scheduling.go:283`) it never reaches the
`select`.

The systemd unit compounds this. `igor-extra/igor-server.service` sets no
`TimeoutStopSec`, so the default (90s on most distributions) applies:

```ini
[Service]
Environment=IGOR_HOME=/home/igor
Type=simple
ExecStart=/opt/igor/igor-server
Restart=always
RestartSec=1
User=igor
```

`systemctl restart` therefore sends SIGTERM, waits the full stop timeout while the process
makes no progress, then SIGKILLs it.

A related but separate defect on the line above: `signal.Notify(sigint, syscall.SIGINT,
syscall.SIGTERM, syscall.SIGKILL)` at `server.go:151` registers `SIGKILL`, which cannot be
caught or handled. It is a no-op and misleading to a reader.

## Reproduction

Any of [BUG-008](BUG-008.md), [BUG-009](BUG-009.md), [BUG-010](BUG-010.md) or
[BUG-012](BUG-012.md) puts the server into the required state. `sudo systemctl restart
igor-server.service` then hangs for the stop timeout before completing — the operator-visible
symptom being "restarting takes a long time, but eventually works".

The database is also not closed cleanly in this path: `sqlDb.Close()` at `server.go:171-172`
is only reached after `wg.Wait()` returns, which it does not, so SQLite is torn down by
SIGKILL rather than closed.

**Not reproduced against a running server.** The mechanism follows from the `Shutdown`
contract and the unit file; the observed slow restarts on the production instance are
consistent with it but have not been instrumented.

## Impact

Recovery from any lock-holding hang requires SIGKILL, delayed by the full systemd stop
timeout. Operators see a restart that appears to hang.

More significantly for diagnosis, it **masks the underlying bug**. The service does
eventually come back, so the incident reads as "restart fixed it" and the wedged goroutine
is destroyed along with any chance of identifying it. A bounded shutdown that logged which
connections were still active at the deadline would have made the class of bugs in this
tracker far easier to find.

SQLite being closed by SIGKILL rather than `Close()` is not a corruption risk on its own —
SQLite is crash-safe — but it does leave the WAL/journal to be recovered on next start.

## Resolution

Fixed in `528e6f0`. All four items below were implemented:

- `shutdownServer` now passes a context bounded by `shutdownGrace` (20s). On deadline it
  logs which service stalled and what that implies — a request blocked on the write lock or
  an external call — then calls `srv.Close()` to force the issue.
- `wg.Wait()` is wrapped in `waitForWorkers`, bounded the same way, so the database session
  at the end of `runServer` is reached even when a manager goroutine is parked.
- `igor-extra/igor-server.service` gains `TimeoutStopSec=60`, comfortably longer than the
  in-process budget so the server reports where it stalled before systemd resorts to
  SIGKILL, and `Environment=GOTRACEBACK=all`.
- `syscall.SIGKILL` removed from the `signal.Notify` call.

`GOTRACEBACK=all` deserves emphasis. Go's default prints only the current goroutine on
SIGQUIT, which is useless for identifying a lock holder. With it set,
`systemctl kill -s SIGQUIT igor-server.service` produces a full dump — operationally the
same as the restart an operator would perform anyway, but with the answer attached.

Covered by `TestShutdownIsBoundedByAStuckRequest` and
`TestWaitForWorkersGivesUpOnAStuckWorker` in
`internal/app/igor-server/shutdown_test.go`. `shutdownGrace` is a `var` rather than a
`const` solely so the second test can shorten it; nothing at runtime reassigns it.

**This fixes none of the hangs.** It bounds recovery from them and — the reason it was done
first — stops the recovery from destroying the goroutine state that identifies the cause.

### Regression and follow-up fix (`6034343`)

The first attempt shipped a regression that reached a testbed. `wg.Wait()` was not only a
shutdown wait — it was the call that kept `runServer` alive for the life of the process
(`exec.go` describes `runServer` as "This call will not return until the server
terminates"). `waitForWorkers` bounded it *unconditionally*, so it also returned after the
grace period with nothing shutting down. `runServer` then closed the database, logged
`GOOD-BYE` and exited 0, and `Restart=always` produced a restart loop with one iteration
per grace period.

Fixed in `6034343`: `waitForWorkers` now blocks on the shutdown channel first and starts
timing only once shutdown has actually been requested. On a running server neither select
case is ready, so it blocks exactly as `wg.Wait()` did.

Two further changes came out of it. The stages of shutdown now share one deadline, set
before the first `Shutdown` call — previously each claimed a full `shutdownGrace`, so two
HTTP servers plus the workers could reach 60s against a `TimeoutStopSec` of 60, leaving no
margin. And `waitForWorkers` takes the WaitGroup and shutdown channel as parameters instead
of reading the package globals, because sharing them let one test's lingering `wg.Wait()`
race the next test's `wg.Add`, which `sync.WaitGroup` does not permit; the race detector
flagged it.

`TestWaitForWorkersBlocksWhileServerIsRunning` covers the regression directly, and
`TestWaitForWorkersHonoursAnAlreadySpentBudget` the shared deadline.

The gap worth recording: the original tests exercised `waitForWorkers` in isolation and
never covered its role in keeping `runServer` alive, which is its primary job. A bounded
wait is correct only in the context that established the bound.

### Original suggested resolution

1. Give `Shutdown` a bounded context, and log what is still outstanding when it expires:

   ```go
   ctx, cancel := context.WithTimeout(context.Background(), 20*time.Second)
   defer cancel()
   if err := srv.Shutdown(ctx); err != nil {
       logger.Error().Msgf("%s did not shut down cleanly within timeout: %v", name, err)
   }
   ```

2. Bound `wg.Wait()` the same way, so the database close at `server.go:171-172` is reached
   even when a manager goroutine is stuck.

3. Add an explicit `TimeoutStopSec` to `igor-extra/igor-server.service` that is comfortably
   longer than the in-process shutdown budget, so the process gets to report why it could
   not stop before systemd kills it.

4. Drop `syscall.SIGKILL` from the `signal.Notify` call at `server.go:151`.

Adding `Environment=GOTRACEBACK=all` to the unit file is worth doing at the same time. It
is not a fix, but it makes `systemctl kill -s SIGQUIT` produce a full goroutine dump, which
is the one artefact that identifies a lock holder unambiguously.
